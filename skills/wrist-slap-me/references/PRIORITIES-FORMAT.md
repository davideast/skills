# PRIORITIES.md format

Keep the file lean: it loads into context every session. Depth lives in linked docs; the law is the tests.

```markdown
# Priorities

<The season, one short paragraph: why these priorities, why now, what
happened that set them. Absolute dates, never "recently".>

## <Priority name>

**Test:** <One sentence a stranger could apply to any proposal.
Phrase as a question: "Does this ...?">

<Two or three sentences, in the user's own words, on what this
priority means in this repo.>

**Counts:** <task categories that serve it>
**Doesn't count:** <the seductive near-misses that feel related but aren't>

**Now:**
- <open task serving this priority>
- <open task serving this priority>
```

## Rules

- **Two or three priorities.** Five is a wish list, and a wish list slaps nothing.
- **The test is the load-bearing line.** Everything else in the section exists to make the test unambiguous. If a proposal's verdict depends on prose outside the test, sharpen the test.
- **"Doesn't count" earns its place** only when a near-miss is genuinely seductive — the kind of work that would be waved through by accident. Don't enumerate the obvious.
- **Now lists are living.** Update them as work lands and starts; they are where the slap's cost line comes from. A stale Now list is the first thing to fix when slaps start feeling hollow.
- **The season paragraph names its trigger.** "First user backed off at the docs" beats "focus is important". When the trigger is resolved, the law is due for revision.
